## Python parser/range follow-ups

1. **Warnings on valid source:** On Python 3.14.2, `PAT = "\d+"` plus a three-row simple-assignment table passes the diagnostic `compareParse` path but the independent AST helper rejects non-empty `SyntaxWarning` stderr. The public dry-run was reproduced as `ALIGN_NOT_ELIGIBLE`. Adding `text=f"{1}"` reaches the formatted-string range helper and fails there. With `PYTHONWARNINGS=error`, the warning becomes a syntax error during `ast.parse`. The follow-up author report says the child scripts now suppress known warning classes while retaining failure checks. The frozen v1 candidate passed the full gate; Opus later identified a distinct raw no-write invalid-source JSON gap. Candidate v2 corrected it, passed the final full gate, and received fix-only Opus PASS.
2. **Pre-existing invalid source response:** For `a=1\nlonger=2\nthird=3\nif:\n`, refusing a write is fail-closed and appropriate. The current raw Python `--write --json` snapshot instead exited 1 with traceback and no JSON, while the baseline emitted its schema-v1 JSON response and exited 0. Public dry-run baseline/current both returned the same `ALIGN_NOT_ELIGIBLE` and diagnostic. The write-path response correction is recorded; Opus found the remaining no-write/check-mode path still omits JSON for a prefix-probe match. Do not accept invalid syntax or change `compareParse` semantics.
3. **Uppercase f-string fallback:** With Python 3.9.6, `F`, `RF`, `FR`, `rF`, and `Fr` prefixes produced no protected range, while lowercase/mixed forms did. This is a range-protection defect on the older STRING-token path. The reproduction did not demonstrate runtime string corruption from uppercase alone. The follow-up author report says the fallback lowercases prefixes and records actual `/usr/bin/python3` 3.9.6. The old focused test log itself omits the runtime version; log it explicitly in future evidence.
4. **CRLF child protocol:** A controlled fake Python child printed `BOXBOX_AST_EQUAL\r\n`; the helper rejected it because the expected marker required LF exactly. This confirms a protocol response issue under simulated CRLF output, not a native Windows run. The follow-up author report says the protocol now accepts only exact LF or CRLF markers while rejecting extraneous output. Opus confirmed this protocol boundary by source inspection; its final verdict still found unrelated open issues.
5. **BOM and lone CR:** The follow-up report attributes BOM rejection to the existing public syntax decoder/check path and calls it pre-existing, not a newly introduced AST-guard regression. Lone-CR line accounting was not tested. Neither is closed by the evidence here.

## A12 cross-language and cost follow-ups

- Valid YAML `value: test ;` reported A12; the suggested deletion would change the decoded scalar from `test ;` to `test;`. A YAML literal block with a semicolon in its body also reported destructive advice. The tested JSON sample `{"note":"foo ;"}` did not report A12. The follow-up author report says A12 is restricted to TypeScript/Python and YAML/JSON scalar regressions were added. Opus confirmed that routing but found broad Python helper failures were silently suppressed. Candidate v2 changed error visibility; focused report tests, the final full gate and fix-only Opus review passed.
- The independent review identified whole-file token checks per TypeScript candidate as a potential `O(candidates × file size)` path. The author report measured about 122 ms for 100 TypeScript candidates across 1,000 lines on this machine, and about 111 ms for a Python sample with one f-string after batching (the initial per-candidate Python sample was about 7,646 ms). These are narrow local measurements, not a general performance guarantee or a large-file bound. A follow-up author report records one 5,000-line/500-candidate sample changing from 3,338 ms to 10.5 ms for report and 7.4 ms for cleanup. This is not a general performance bound; broader characterization is outside this bounded review; the candidate v2 fix-only review closed the reported helper-error finding.
