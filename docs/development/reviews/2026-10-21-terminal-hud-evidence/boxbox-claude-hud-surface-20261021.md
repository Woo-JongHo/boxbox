## Official supported surfaces

Claude documents `statusLine` as a persistent terminal bar fed session JSON on stdin; stdout is rendered after a successful exit. It runs at session start and selected session events; optional `refreshInterval` adds idle refresh. Workspace trust is required, and policy can suppress custom status lines. A command should stay fast and use safe fallbacks for unavailable data. The current documentation includes newer optional fields; validate any chosen optional field against the installed build before depending on it. [Official status-line guide](https://code.claude.com/docs/en/statusline).

Official mods support begins at **2.1.287 in the terminal**, or **2.1.286 in the Desktop app's own bundled Claude**. Therefore installed terminal 2.1.286 is below the documented general-support floor, despite exposing mod-related CLI commands. Do not infer a Desktop version from this terminal binary. Drawing is unavailable in `claude -p`; print-mode success is not visual acceptance. [Official mods overview](https://code.claude.com/docs/en/plugins/mods/overview).

A mod's hook JSON names its module through `modules`. The module exports `register(on, options)`. `ui.render` at `AbovePrompt` is documented for terminal and Desktop, and `$.ui.resolve(e)` supplies drawing components. The reference covers CLI/Desktop as of 2.1.290; exact runtime declarations generated by the target build take precedence. AbovePrompt is not the VS Code chat-panel surface. [Official mods reference](https://code.claude.com/docs/en/plugins/mods/reference).

Official validation statically inspects a mod without executing it; starting a compatible host with `--plugin-dir` loads it for one session. That host writes its type declarations near the mod. Use those declarations rather than guessing APIs from an unrelated release. [Official authoring guide](https://code.claude.com/docs/en/plugins/mods/create).

## Configuration preservation design

1. Resolve the applicable settings path and read only the current `statusLine` plus necessary precedence flags. Preserve all unrelated bytes/keys; never replace the full settings object with a minimal sample.
2. If absent, create the BoxBox entry through an atomic merge with backup and compare-before-write. If already BoxBox-owned, update idempotently. If another status line exists, leave it active and report a concrete conflict; a composition or explicit replacement choice is a separate action.
3. Keep the command on a stable installed launcher path rather than a versioned plugin cache. Quote paths with spaces, bound stdin size, sanitize terminal control characters in file-derived fields, and avoid executing project-provided commands.
4. Uninstall restores the previous key only if the current key is still the one BoxBox wrote; do not undo subsequent user edits.

These are implementation recommendations, not changes made in this task.
