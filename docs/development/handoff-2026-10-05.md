# 배포 구현·DATA2 검증 Handoff — 2026-10-05

이 문서는 다른 AI가 **현재 작업 트리를 읽기 전용으로 독립 검증**하고, 필요하면 DATA2를 이어서 구현할 수 있도록 작성했다. 제품은 아직 배포되지 않았다. 이 문서의 숫자는 명시된 실행 시점과 범위의 실측 또는 기록이며, 사람의 규칙 승인이나 최종 감사 결과로 해석하면 안 된다.

## 1. 임무와 절대 경계

- 사용자 목표: TypeScript·Python 핵심 기능, 엔진 CLI, 얇은 에이전트 플러그인을 실제 공개 배포 가능한 수준으로 완성한다. 그 외 8개 언어는 첫 공개의 동등 품질 완료 조건이 아니다.
- 현재 단일 active 작업: `docs/plan.md`의 **DATA2 후보 판정·보류 사례 해소**. 다음 순서는 같은 계획의 REL 작업표를 따른다. 제품명, 라이선스, 공개 채널, 사람의 규칙 승인은 미결정이다.
- 배포 데이터는 내부 연구 Evidence, 제작자 소유 preset, 설치 사용자 전역 DB, 프로젝트 DB로 분리한다. 관측 수나 AI·기계 검증을 사람 승인으로 바꾸지 않는다.
- 제3자 원문이 든 `.boxbox/cache/corpus/`와 로컬 `~/.cache/boxbox/corpus/`는 공개 artifact와 git에 넣지 않는다. 다른 AI가 검증 결과를 공유할 때에도 원문 전체, 로컬 경로, 개인 코드 예문을 외부 서비스에 붙여 넣지 않는다.
- 현재 작업 트리는 **57개 변경/신규 항목이 있는 미커밋 상태**다. 브랜치 `m1-safety-proof`, HEAD `8338798187295b1c2cd9b737750cb84d22297f32`, upstream보다 27커밋 앞섰다. 다른 작업의 편집도 섞여 있으니 일괄 초기화·복구·정리하지 않는다. 재개 시 `pwd`와 `git status --short --branch`부터 다시 확인한다.
- 현재 세션에서 commit, tag, push, publish는 실행하지 않았다. 다른 AI의 읽기 전용 판정 역시 릴리스 승인과 다르다.

## 5. 독립 검증 순서와 기대 결과

명령은 저장소 루트에서 실행한다. 다른 AI가 읽기 전용 검토만 맡는다면 빌드/테스트가 만드는 `dist/`, 임시 파일, cache 변경 가능성을 먼저 구분하고 기존 파일은 덮어쓰지 않는 별도 checkout에서 실행한다.

```bash
pwd
git status --short --branch
git rev-parse HEAD
cat .boxbox/cache/corpus/summary.json
bun test test/corpus-candidates.test.ts test/corpus-evidence.test.ts
bun test test/public-preset.test.ts test/public-artifact.test.ts
bun run check
bun run pack:cli
git diff --check
```

마지막 **전체** `bun run check` 기록은 403 pass / 5 skip / 0 fail, 45개 파일·408개 테스트이며 tsc와 `bash -n install.sh`도 통과했다. 이어 추가 assertion 뒤 타깃 2개 파일 검사는 10 pass / 0 fail, `bunx tsc --noEmit`, shell 문법, diff 검사가 통과했다. 위 명령을 이 Handoff 작성 시점에 다시 전부 실행한 것은 아니다. Rust 3개·Kotlin 2개 skip은 성공으로 세지 않는다. `pack:cli`의 기대 내용은 위 6개 파일과 빈 preset이며 **현재 작업 트리 재실행 수치는 달라질 수 있다.** 생성물에 `observations.jsonl`, `examples.jsonl`, checkout, `.boxbox/cache`, 로컬 DB, 미승인 후보 문서가 없는지 tarball 목록과 내용 scan으로 독립 확인한다.

자료 재생성은 읽기 전용이 아니다. `bun scripts/corpus-candidates.ts --limit 40 --reps 1`은 `.boxbox/cache/corpus/`을 원자 교체하고 대표 수/선택 범위를 바꾸므로, **현재 225개 cache를 보존할 때에는 직접 실행하지 말고 `--output`으로 별도 임시 디렉터리를 지정**한다. 동일 225개를 재생성하려면 기존 생성 방식의 기본 40키/3대표가 아니라 모든 키를 선택해야 하므로 `--limit 88 --reps 3 --output <temporary>`를 쓴다. 입력 cache의 8개 checkout이 있어야 하며 소요 시간이 크다. 재생성 전후의 수치가 다르면 원본 HEAD/hash, 엔진 변경, timeout 환경을 따로 기록한다.

정렬 자체와 후보 행 매핑을 혼동하면 안 된다. 첫 11건은 정렬기 parser·고정점이 통과한 뒤 `beforeLines.length !== afterLines.length`에서 실패했다. 이 성공은 해당 **후보의 전후 예문 승인**이 아니다. timeout 1건은 parser 상태도 `not-run`이다.

## 6. 다른 AI에게 요청할 독립 검증 질문

1. `scripts/corpus-candidates.ts`의 11개 line mapping 보류를 각각 실제 원본 hash/commit과 임시 정렬 결과로 재현한다. 전체 줄 수 변화가 관측 범위 **앞/안/뒤** 중 어디서 생겼는지 구분하고, 행 대응을 안전하게 확정할 수 있는 경우에만 근거와 회귀 테스트를 제안한다. 구조가 바뀐 표는 실패로 남긴다.
2. `example-14c84...`의 60초 timeout을 재현·측정한다. 첫 실행/두 번째 고정점/TS AST pass/child process 중 어디에 시간이 쓰이는지, 종료 시 원본·임시 파일이 보존/제거되는지 확인한다.
3. 상위 4개 키의 대표 예문을 읽고 문법 보존 외에 의미 있는 같은 역할 행인지, 과도한 padding이나 인접 무관 행 결합이 없는지, 2행 예외와 Python 들여쓰기·문자열·주석 반례를 검토한다. 사람이 승인할 후보 제안은 가능하지만 `approved` DB 적재는 하지 않는다.
4. `scripts/public-preset.ts`의 closed schema, duplicate-key 정규화, Decision 승인 절 추출과 실제 tarball allowlist를 공격자 관점에서 확인한다. preset이 비어 있다는 사실과 개인정보·원문 유사성의 의미 판정 불가를 결과에 명시한다. 이전 제한적 Sol 검토는 `docs/reviews/2026-10-04-public-preset-db-boundary.md`에 있다.
5. 공개 경계가 **두 개**라는 점을 확인한다. npm CLI tarball은 allowlist 방식이지만 marketplace `source: "./"`는 전체 저장소를 참조한다. 플러그인 공개 때 내부 Evidence/연구 파일과 실행 구현 노출이 가능한지 실제 host packaging/discovery로 확인해야 한다.
6. 테스트 통과, 코드 자체 정렬, 실제 host 수용, 사람 승인, 최종 감사, registry publish를 별개 상태로 판정한다. 발견사항은 file:line·재현 명령·입력/출력·영향·수정 제안·미확인 항목으로 남긴다. 서로 다른 provider의 검토라면 해당 모델/버전과 읽기 전용 여부도 적는다.

## 7. 배포 전 남은 작업과 결정

우선 DATA2의 12건을 위 방식으로 해소하고 상위 후보의 일반화/반례를 정리한다. 사람에게 제시할 규칙 후보에는 조회 키, 적용 범위, synthetic 긍정/부정 예문, 원본과의 차이, Decision 근거, hash가 필요하다. **현재 인간 승인 0건이므로 preset은 비어 있어야 한다.** 그 다음 REL6/7 설치본의 실제 승인 여정을 검증한다.

독립적으로 진행 가능한 다음 제품 작업은 REL9 얇은 플러그인 어댑터와 실제 호스트 discovery·출력 수용 검증이다. REL10은 지원 OS에서 clean install→init→doctor→check→format→recheck→host→update→remove와 사용자 DB 보존을 요구한다. 사용자 DB add/import/backup 경험, TS native timeout 안전성, 공개 write inventory도 남았다. REL11에서는 marketplace 전체 repo source 분리, 제품명·라이선스·채널 확정, `private` 해제, 영어 문서, CI matrix, secret/제3자 원문 검사, 실제 artifact 목록/hash를 동결한다. REL12의 tag/push/publish와 공개 artifact 재설치는 그 뒤다.

전용 ESLint는 없다. 최근 커스텀 정렬기 읽기 전용 조사에서 TS 128개 파일, 표 1,027개 중 990개 정렬·37개 미정렬로 나왔고 37개는 기존 `scripts/eval.ts` 한 파일이었다. 이는 lint 적용률이나 엔진 품질 비율이 아니다. 수정한 파일에서는 TODO, `test.skip`/`.only`, 미구현 분기와 자체 정렬을 별도로 검사한다.

## 8. 판정 기록 방식

다른 AI는 검증 결과를 새 `docs/reviews/YYYY-MM-DD-...md`에 기록할 수 있다. 검토 전용 패스에서는 제품 코드와 승인 DB를 수정하지 않는다. 결과에는 (a) 확실한 finding과 재현, (b) 검증된 정상 범위, (c) 미실행·환경 제약, (d) 추천 수정 순서, (e) 사용한 commit 및 dirty tree 여부를 분리한다. 기존 문서나 작성자의 자기 판정을 그대로 승인하지 말고 실제 명령과 artifact를 대조한다. 특히 외부 provider 최종 감사가 미실행이면 **미실행 blocker**로 남기고 다른 모델의 성공으로 대체하지 않는다.
