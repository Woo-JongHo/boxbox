# 99_www 파일럿 — `;`·`=` 어긋나는 곳은 어디서 왔나 (2026-09-26)

woo-readability 플러그인의 신규 언어 엔진 작업과 병행해, 99_www 전체(src + scripts, 349개 파일)를 대상으로 표형 가독성 검사기(TypeScript AST 기반 `06_align-tables.ts`)가 `=`·`;` 열 어긋남을 어디까지 잡는지 측정했다. 검사기는 플러그인 단일 소스(98_Plugin)에서 실행해 www 저장소는 읽기만 했다.

## 측정 방법

1. 전체 파일을 훑어 `const/let/var` 단일 선언 행의 `=`·`;` 열을 실측하고, 같은 모양 행이 3행 이상 연속으로 이어지며 열이 어긋난 구간(런)을 수집했다.
2. 각 런이 검사기 보고 그룹에 속하는지 교차분류했다.
3. 그룹 밖으로 남은 런은 실제 코드를 줄별로 읽어 원인을 분류했다.

## 결과 요약

| 분류 | 수 | 성격 |

| └ 커버 안 됨 | 9 | 전수 확인 결과 전부 계약상 정당한 거부(아래 표) |
| 전체 파일의 `;` 미정렬 감사 | t-notes.ts:5 등 | **검사기가 잡아내는 진짜 drift** — 최근 편집 뒤 재잠금이 안 된 파일 |

9곳의 "커버 안 됨"을 줄별로 읽은 결론:

- **혼합 행(한 줄 다중 문장)** — `const dir = this.artifactsDirectory(); await this.ensureDirectory(dir);` (planning-store.ts:78, development-vault.ts, delegation.ts 등). 한 행 = 한 문장이라는 엑셀 계약상 표 행이 아니므로 검사기가 거부하는 것이 맞다. 이런 줄은 검사기가 아니라 가독성 작업 흐름(사람+검사자)이 여러 행으로 재구성한 뒤 잠근다.
- **다중 선언자** — `const s = this.get(), heading = executionHeading(s);` (www-surface.ts:271, workbench-config.ts:74, request-runtime.ts:211). 마찬가지로 한 행에 이름-값 쌍이 여러 개라 엑셀 표의 한 행으로 볼 수 없다. 검사기는 혼합 행을 건너뛰고 **순수 행만 3행 이상이면 별개 표로 정확히 잠근다**(www-surface 272-279, request-runtime 208-210, git-commit-control 163-165, benchmark 251-253에서 실증).
- 나머지 눈에 보이는 어긋남의 대부분은 **2행 페어**다(예: commit-governance.ts:74-75). 계약상 2행은 사용자가 비교 효용을 확인한 경우에만 표로 승격한다. 승격하려면 `06_align-tables.ts --file <파일> --min-rows 2`를 쓰면 된다 — 메커니즘은 이미 있다.

## 결론

1. **검사기의 `=`·`;` 축 탐지와 정렬은 정상 동작한다.** ≥3행 순수 런에서 미탐지 사례를 하나도 찾지 못했다. grid-kinds 보강은 불필요했다.
2. www에서 어긋남이 보이는 진짜 원인은 세 가지다: ① 혼합 행·다중 선언자(재구성 필요), ② 2행 페어(승격 정책 필요), ③ 편집 뒤 재잠금 미실행 파일(t-notes.ts:5 `misaligned=1` — 검사기가 바로 잡아낸다).
3. 권고 다음 단계: www 전체에 `00_normalize-imports` → `06_align-tables --file` 검사 루프를 돌려 drift 파일 목록을 뽑고, 혼합 행은 가독성 작업 흐름으로 재구성한 뒤 잠근다. 대량 `--write`는 www 커밋 거버넌스($woo-commit)와 별도로 사용자 승인을 받아 진행한다.
